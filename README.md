# SLT-MOBITEL Customer Churn Analysis — Decision Analytics Prototype

A Laravel + MongoDB web application that analyses telecom subscriber churn from
synthetic data. It provides authentication, full create/read/update/delete
workflows for the customer and plan catalogues, MongoDB aggregation dashboards,
and a transparent rule-based churn risk score with a retention focus.

> **All data in this application is synthetic.** Every customer, subscription,
> payment, usage record and complaint is generated by the seeder. Nothing here is
> real SLT-MOBITEL data, and no figure produced here is official SLT-MOBITEL
> reporting. The prototype is not affiliated with or endorsed by SLT-MOBITEL.

## Installation

```bash
composer install
npm install
cp .env.example .env          # Windows: copy .env.example .env
php artisan key:generate
```

Configure MongoDB in `.env`:

```dotenv
DB_CONNECTION=mongodb
MONGODB_URI=mongodb://127.0.0.1:27017
MONGODB_DATABASE=slt_mobitel_churn
```

Create the collections and their indexes, then load the data:

```bash
php artisan migrate
php artisan db:seed
```

Build the frontend assets:

```bash
npm run build        # or: npm run dev   (hot reload during development)
```

Start the application:

```bash
php artisan serve
```

Open <http://127.0.0.1:8000> and sign in.

## Rebuilding the dataset

The generator is deterministic, so the same command always reproduces the same
figures. To clear the synthetic collections and regenerate them:

```bash
php artisan churn:reseed
php artisan churn:reseed --customers=1000    # smaller dataset
php artisan churn:reseed --months=24 --customers=7500
```

`churn:reseed` deletes documents with `deleteMany` rather than dropping the
collections, so the indexes created by the migrations survive.

Default volume produces 7,500 customers, 8,071 subscriptions, 94,805 usage
records, 222,986 payments, 13,048 complaints, 7,500 churn records and 12 plans —
approximately 354,000 documents. The churn target is 31.5% and the seeded run
marked 2,328 customers as churned (31.0%).

Two different churn figures appear in the interface on purpose. The dashboard and
Churn Analysis KPIs count customers whose master record says `Churned`
(2,169 — 28.9%), while a churn record exists for every churned customer and
records `Churned` for all of them; the 159-customer difference is the share of
churners stored with the master-record status `Terminated`.

## Writing data: customers and plans

Customers and plans are editable through the UI; the other six collections are
maintained by the generator so analytics stay reproducible.

- **Validation.** Every write goes through a form request
  (`App\Http\Requests`) that enforces the controlled vocabulary, numeric ranges,
  formats and ID uniqueness. Invalid input is returned to the form with the
  messages attached to the offending field; nothing is partially written.
- **Business keys are immutable.** `customer_id` and `plan_id` are stored as plain
  string references in five dependent collections, so an update that tries to
  rename one is rejected rather than leaving orphaned documents.
- **Destructive actions are confirmed.** Deleting requires the identifier to be
  typed back in, and the delete views first report how many dependent documents
  are affected.
- **Referential integrity without transactions.** MongoDB runs standalone in this
  project, which has no multi-document transactions.
  `App\Services\ReferentialIntegrityService` therefore deletes leaves before
  their owner. Deleting a customer removes that customer's `churn_records`,
  `complaints`, `payments`, `usage` and `subscriptions`; deleting a plan is
  blocked while subscriptions still reference it unless the cascade is
  explicitly confirmed, and even then only the subscriptions are removed.
- **Malformed identifiers never reach a controller.** Route patterns
  (`C` followed by digits for customers) return a 404 rather than a validation
  redirect, so a hand-edited URL cannot trigger a query.
- **No role gate.** Any authenticated account can write. Seeded accounts are
  `admin@` and `analyst@`; there is no per-user permission model.

## The risk model

The risk score is a **project-defined rule-based model**, not a trained machine
learning classifier. It is evaluated for retained subscribers only, against the
latest reporting month in the dataset.

| Factor | Condition | Weight |
| ------ | --------- | ------ |
| Low Usage | Latest month's data usage below the low-usage threshold | +20 |
| Multiple Complaints | Two or more complaints recorded | +20 |
| Long Recharge Gap | Prepaid subscriber with a long gap since the last recharge | +20 |
| Short Tenure | Subscription tenure below the short-tenure threshold | +15 |
| High Monthly Cost | Monthly charge above the high-cost threshold | +15 |
| Service Issue | At least one complaint still Open or In Progress | +10 |

Bands:

| Score | Level |
| ----- | ----- |
| 60–100 | High |
| 30–59 | Medium |
| 0–29 | Low |

Two deliberate design decisions:

- **"Days since recharge" is measured against the latest payment date present in
  the dataset**, not the system clock. This keeps results reproducible regardless
  of when the prototype is run.
- **The recharge-gap factor cannot trigger for postpaid subscribers**, because
  postpaid customers have no recharges. Their value stays null rather than being
  counted as a risk signal.

Thresholds, weights and bands are all configurable in
`config/churn-analytics.php`; the factor weights are applied inside the
aggregation pipeline, so changing a weight changes the score without a re-seed.

## Data model

All eight collections live in MongoDB. There is no relational database anywhere
in the application.

| Collection | Purpose | Key indexes |
| ---------- | ------- | ----------- |
| `users` | Application login accounts | `email` unique |
| `plans` | Tariff catalogue | `plan_id` unique, `plan_type` |
| `customers` | Subscriber master record | `customer_id` unique, `district`, `customer_status`, `customer_segment`, `customer_status + district` |
| `subscriptions` | Which plan a customer holds | `subscription_id` unique, `customer_id`, `plan_id`, `status + plan_id`, `customer_id + status + tenure_months` |
| `usage` | Monthly consumption per customer | `usage_id` unique, `customer_id`, `month`, `customer_id + month` |
| `payments` | Recharges and bills | `payment_id` unique, `customer_id`, `date`, `payment_status`, `payment_type`, `customer_id + date` |
| `complaints` | Service complaints | `complaint_id` unique, `customer_id`, `category`, `severity`, `status`, `customer_id + status` |
| `churn_records` | Churn outcome and retention action | `customer_id` unique, `churn_status`, `churn_reason`, `churn_date`, `retention_action` |

Sessions and cache use file storage: the MongoDB query grammar does not
implement `insertOrIgnore`, which the database session and cache stores both
require. Application data is unaffected.

## How the synthetic data is generated

The generator is deliberately *story driven* rather than uniformly random. Each
customer first receives a latent churn outcome, and every downstream collection
is derived from it:

- Churned customers show declining usage before they leave, more complaints,
  wider recharge gaps and shorter tenure.
- A share of **retained** customers show early disengagement signals
  (reduced usage, complaints clustered near the end of the window, stopped
  recharging) without having left yet. Without this cohort the High risk band
  would always be empty and the model would appear not to work.
- Price-driven churners keep consuming up to their last bill, so their usage is
  not modelled as declining.

History windows are anchored to each customer's reference month — their churn
month, or the end of the reporting window for retained customers — rather than to
the start of the window. This is what keeps a retained customer's most recent
transaction recent, which the recharge-gap factor depends on.

Names, phone numbers and email addresses are obvious placeholders; districts are
public administrative geography; every numeric attribute is generated.

## Architecture notes

- **Aggregation over fetching.** Dashboards are computed with MongoDB aggregation
  pipelines (`$lookup`, `$facet`, `$group`, `$switch`, `$dateDiff`) rather than by
  loading documents into PHP. The risk table uses a single `$facet` pass so the
  band summary, row count and page are computed together.
- **`MongoAggregator`** is a thin, typed wrapper over the native MongoDB driver so
  services never call raw collection methods.
- **Controlled vocabulary.** Churn reasons, complaint categories, statuses,
  segments and risk bands come from `App\Support\ChurnVocabulary` and are
  validated in the controllers, so a hand-edited URL cannot inject an arbitrary
  match into a pipeline.
- **Lazy loading is disabled** in `AppServiceProvider`, so a missing eager load
  fails loudly in development rather than issuing an N+1 query.
- **Batched seeding.** At full volume the dataset is roughly 354,000 documents,
  so `generateInBatches()` yields slices and the seeder inserts each one, which
  keeps the CLI within its memory limit. Its output is identical to `generate()`
  for any batch size, and `tests/Feature/SyntheticGeneratorTest.php` asserts that.
- **Churn trend is a cohort, not a count of exits.** Retained customers carry a
  null `churn_date`, so they cannot be counted by matching on that field. The
  monthly chart therefore derives them: base (cumulative registrations) minus
  everyone lost up to that month. `rate` is the monthly churn rate of that
  cohort's base. Both series are grouped server side into one row per month.
- **One query input per request.** The reporting month and the risk band counts
  are each resolved once and shared by the methods that need them. The band
  counts come from the six-join risk pipeline, so resolving them per method
  doubled the dashboard's database time for an identical result.

## Testing

```bash
php artisan test
php artisan test --filter DashboardPageTest
```

Feature tests cover authentication and route protection, dashboard rendering
with the synthetic disclaimer, customer browsing and filtering, the churn
analysis breakdowns, the monthly churn trend against the stored churn outcomes,
the risk table's ordering, filtering and pagination, the internal consistency of
the risk band counts, the customer/plan write side (validation and vocabulary
rejection, unique and immutable business keys, confirmation-gated deletion, and
the dependent-document cascades), and the synthetic generator's referential and
status invariants.

Tests read the same MongoDB database as the application, so run `php artisan
db:seed` first.

## Configuration reference

`config/churn-analytics.php` holds:

- `prototype.label` and `prototype.disclaimer` — the wording shown on every page
- `seeding.customer_count`, `seeding.usage_months`, `seeding.churn_rate`,
  `seeding.chunk_size`
- `risk.weights`, `risk.thresholds`, `risk.bands`, `risk.max_score`

Overriding seed volume via environment variables is supported for smaller local
runs:

```dotenv
CHURN_SEED_CUSTOMERS=500
CHURN_SEED_USAGE_MONTHS=12
CHURN_SEED_CHURN_RATE=0.315
CHURN_SEED_CHUNK=1000
```
